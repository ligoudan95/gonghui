## 1. 修订目的

上一版设计案已经确立“工会筹备—远征探索—战棋目标—结果回响”的核心体验，但仍有部分规则停留在原则层，无法直接指导实现、存档和测试。本修订包把原则落成四类可执行定义：

1. **状态定义：**任何行动处于什么阶段、允许什么操作、什么时候推进世界。
2. **账本定义：**资源、状态、支援和奖励如何扣除、获得、冻结和恢复。
3. **一致性定义：**存档、重试、崩溃和重复操作不会复制奖励、吞掉损失或产生软锁。
4. **验收定义：**每条 P0/P1 风险都有对应规则、变量和测试用例。

本修订包不改变原案的核心方向，不新增完整派遣、复杂恋爱、随机任务生成或第二区域；它优先补足原案已经承诺但尚未写死的边界。

## 2. 文档优先级

当不同文档出现冲突时，按以下优先级解释：

1. 本索引中标记为“冻结规则”的条款。
2. `01`、`02` 中关于状态、结算和存档的一致性规则。
3. `DEMO/01`、`DEMO/02` 等 DEMO 专用规则；DEMO 的具体数值覆盖正式版的建议区间。
4. 其他正式版系统策划案中的建议基线。
5. 原始设计案中的原则性描述。

原始文档保留为历史基线，不直接删除或覆盖：

- `冒险者工会游戏初步设计案.md`
- `DEMO/DEMO策划文档.md`

如果实现或内容配置必须违背冻结规则，必须先在变更记录中说明原因、受影响的存档字段和新增测试用例。

| 风险 | 严重度 | 规则文档 | 必须有的测试 |

| 主线实际依赖特殊 NPC | P0 | 05、06 | 无 NPC、低资源、失败后基础路线 |

## 6. 规则标签

每条规则在后续文档中使用以下标签：

- **[冻结]**：实现不得自行解释；变更必须经过范围评审。
- **[基线]**：当前推荐数值或实现方案，可在测试后调整，但必须记录前后差异。
- **[待定]**：正式版仍需通过原型或玩家测试决定，DEMO 不得依赖它。
- **[禁止]**：不允许用内容例外绕过。
- **[测试]**：必须转化为自动化或人工验收用例。

## 7. 实施顺序与门禁

### M0：规则冻结

完成 `01`、`02` 的状态、结算和存档定义；所有其他文档引用统一术语。未完成前不得接入复杂内容分支。

### M1：状态灰盒

可以走通“接受任务—出发—节点—战棋—结果—回城”，能模拟成功、部分成功、撤退和失败；没有重复奖励和软锁。

### M2：资源与内容接入

完成 `03`–`07` 的基础账本、任务、支援、地图和队伍状态；至少有一条不依赖特殊 NPC 的基础主线。

### M3：公平性与可读性

完成 `08` 的随机种子、难度锁定、结果解释和坏运气保护；完成日志和因果回顾。

### M4：交付验收

完成 `09` 与 DEMO-06 的测试；连续五次完整成功/失败路径无阻断、无重复奖励、无软锁，且 DEMO 首次游玩中位时长在 60–70 分钟。

## 8. 变更流程

任何新增或修改系统必须同时提交以下信息：

```text
变更编号：
变更目标：
对应核心卖点：经营 / 探索 / 战棋 / 特殊NPC支援
新增或修改的状态变量：
是否影响存档结构：
是否影响结算顺序：
是否影响资源净收益：
是否影响主线基础解法：
新增测试用例：
为此变更砍掉的内容：
回滚方式：
```

以下情况必须拒绝直接合入：

- 只增加奖励，没有写消耗或失败后果。
- 只增加分支，没有写存档和变量回写。
- 只增加支援，没有写无支援基础解法。
- 只增加随机性，没有写种子和结果解释。
- 只增加危机，没有写最低恢复路径。
- DEMO 新增系统但没有明确砍掉同等规模内容。

## 9. 交付前必须关闭的问题

- [ ] 所有行动状态有进入、退出和禁止操作。
- [ ] 所有一次性奖励和支援消耗有唯一标识。
- [ ] 战棋重试不会复制奖励或免费回滚不可回滚后果。
- [ ] 准备行为不会无限推进资源而不推进世界。
- [ ] 资金归零、补给归零、全员受伤时仍有可玩路径。
- [ ] 主线无特殊 NPC、低资源和失败后都有基础解法。
- [ ] 节点回访不会重复领取一次性内容。
- [ ] 政策和难度不能在结果已知后规避代价。
- [ ] 随机结果能说明主要影响因素。
- [ ] DEMO 的变量字典和测试清单与实现字段一致。

## 10. 仍待正式版决定的问题

以下问题不阻塞 DEMO，但不得在实现中默默决定：

- 正式版是否允许高风险模式永久死亡。
- 正式版是否支持二周目继承信息。
- 正式版支援联络位的长期扩容曲线。
- 恋爱路线的最终数量与个人结局演出规模。
- 正式版章节之间是否保留全部支援次数与债务。
