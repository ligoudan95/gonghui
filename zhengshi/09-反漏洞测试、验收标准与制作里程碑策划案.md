## 1. 测试目标

本文件不是“发现问题后再补测试”的清单，而是所有核心规则进入实现前的交付门槛。测试必须验证三件事：

1. **不会作弊式增益：**重复领奖、读档合并、节点刷取、支援叠加和无限准备不能使资源净增而不承担成本。
2. **不会玩家软锁：**全员受伤、资金归零、补给归零、支线延后、任务失败和存档中断都能到达可理解的下一步。
3. **不会规则黑箱：**玩家能知道结果原因、支援代价、期限后果、风险来源和可用基础解法。

未执行的用例不得标记为“通过”；“设计上应该不会发生”不等于测试证据。

## 2. 严重度与关闭条件

| 等级 | 定义 | 交付要求 |
|---|---|---|
| P0 | 可复制奖励、资源账本错误、存档污染、主线软锁、结算重复、不可继续 | 发布前零开放项；修复后必须回归原用例 |
| P1 | 明显最优刷法、支援保险、政策/难度套利、关键线索硬卡、状态不可解释 | DEMO 外部试玩前零开放项；正式版可有明确监控项 |
| P2 | UI 表述、日志缺失、节奏、非阻断表现和数值偏斜 | 必须有负责人、版本和已知问题说明 |

### 2.1 P0 关闭证据

每个 P0 问题必须同时提供：

- 修复前复现存档或最小复现步骤。
- 修复后的同一用例结果。
- 资源、状态、任务、地图、NPC 和日志的前后差异。
- 至少一次强退/重载回归。
- 若修改存档结构，提供迁移或旧档兼容说明。

## 3. 测试环境和数据准备

### 3.1 固定测试夹具

```text
fixture_empty_start
fixture_low_resources
fixture_all_injured
fixture_pending_result
fixture_combat_start
fixture_settled_epoch
fixture_old_content_version
fixture_debug_only
```

每个夹具必须写明：

- `save_schema_version`、`game_build_id`、`settlement_epoch`、`cycle_id`。
- 资金、补给、情报 facts、声望、债务、联络位。
- 冒险者伤病/疲劳/压力/士气和可用队伍。
- 当前任务、节点四组状态、支援次数/冷却。
- 随机种子和随机流游标。

### 3.2 断言维度

每个测试至少检查：

- 资源账本：committed、reserved、debt 是否符合预期。
- 唯一性：`result_id`、`commit_id`、`claim_key` 是否重复。
- 状态机：阶段、任务、节点和支援状态是否合法。
- 时间：`cycle_id`、`world_cycle`、`local_tick` 是否只按规则变化。
- 结果：奖励、伤病、世界 flags、NPC 后果和日志是否一致。
- 读档：整包恢复且不跨 epoch merge。

## 4. 状态机与结算测试组

| ID | 操作 | 预期 |
|---|---|---|
| TC09-01 | 依次完成筹备、锁定、远征、节点、战棋、结果、回响 | 每次只进入合法阶段，禁止操作有原因码 |
| TC09-02 | 从 `COMBAT` 请求回工会 | 被拒或转为合法撤退，不清除已发生状态 |
| TC09-03 | 结果预览取消 | 不提交资源、奖励、伤病或世界 flags |
| TC09-04 | 同一 `result_id` 提交两次 | 第二次无账本增量，返回第一次结果 |
| TC09-05 | 任务和节点同时结算 | 一个 `commit_id` 原子提交，周期只关闭一次 |
| TC09-06 | 结算事务中模拟写入失败 | 整笔回滚或按日志恢复，不留下半状态 |
| TC09-07 | 周期关闭请求发送两次 | 维护、恢复、期限和 `cycle_id` 只执行一次 |
| TC09-08 | 回响强退后重载 | 已消费回响不重复，未消费回响仍可处理 |

## 5. 存档、读档和重试测试组

| ID | 场景 | 预期 |
|---|---|---|

## 6. 经济和刷取测试组

| ID | 场景 | 预期 |

## 11. 内容和体验验收

### 11.1 内容完整性

- [ ] 玩家三次以内理解筹备—远征—结算流程。
- [ ] 至少一次筹备选择改变地图或战棋条件。
- [ ] 至少一项特殊 NPC 助力完成“解锁—调用—反馈”闭环。
- [ ] 无特殊 NPC 时主线仍有可理解基础路线。
- [ ] 普通冒险者互动没有主角好感、恋爱或主线硬锁。
- [ ] 战棋至少两个竞争目标和三种自然结果。
- [ ] 失败、撤退和部分成功都有结算和下一步钩子。

### 11.2 因果可读性

- [ ] 玩家能解释为什么进入战棋。
- [ ] 玩家能看到任务结果的主要影响因素。
- [ ] 助力调用前能看到作用、时机、次数、代价和限制。
- [ ] 失败后两分钟内进入可读结算。
- [ ] 重要不可逆选择有预告。
- [ ] 日志能回溯资源和世界变化来源。

### 11.3 节奏指标

- 首次游玩中位时长：45–75 分钟；DEMO 推荐 60–70 分钟。
- 熟悉后完成核心闭环：35–55 分钟。
- 结算回响：5–10 分钟内完成，不连续弹出无法跳过的深度支线。
- 主战棋不因重复清场和无目标战斗拖长。

## 12. 制作里程碑

### M0：规则冻结

交付：00–08 的术语、状态、账本、支援、节点、队伍和随机边界；所有 P0 规则有对应测试 ID。

门槛：没有“实现时再决定”的状态转换和结算顺序。

### M1：状态灰盒

交付：能走通筹备、远征、节点、战棋、结果和周期关闭；失败、撤退和强退可恢复。

门槛：TC09-01 至 TC09-18 的核心状态和存档用例通过记录完成。

### M2：经济与内容接入

交付：资源账本、准备动作、任务实例、三类支援入口、节点四组状态和队伍状态。

门槛：TC09-19 至 TC09-52 中的 P0/P1 用例没有开放缺陷。

### M3：体验和公平

交付：结果原因、助力代价、随机种子、难度锁定、基础解法和失败恢复 UI。

门槛：首次玩家能在不查外部攻略情况下完成或接受至少三种结果。

### M4：交付稳定性

交付：自动存档、坏档恢复、调试工具隔离、内容版本说明和已知问题表。

门槛：连续五次成功/失败/撤退组合流程无阻断、无重复奖励、无软锁；发布包不包含开发调试入口。

## 13. 变更和回归规则

任何规则变更都必须：

1. 更新 00 的追踪矩阵或说明不影响哪些风险。
2. 更新相关变量字典和存档版本说明。
3. 增加或修改至少一个测试用例。
4. 重新执行受影响的 P0/P1 回归组。
5. 在变更记录中写明砍掉、延后的内容和测试成本。

禁止以“只改文案”“只改奖励”“只改 UI”绕过测试：只要改变了结果、成本、条件、提示或读取字段，都需要至少进行对应回归。

## 14. 交付结论

本案的“通过”不是测试数量达到某个数字，而是确认四种闭环都能被重复验证：

```text
筹备选择 -> 远征状态 -> 结果提交 -> 周期变化
支援解锁 -> 合法调用 -> 明确代价 -> 支援反馈
节点调查 -> 事实/物证 -> 回访变化 -> 奖励不重复
失败结果 -> 可读后果 -> 恢复路径 -> 继续推进
```

所有表格只是测试定义，未执行前不得写成已经通过；正式版和 DEMO 的实测结果必须保存到各自版本记录中。
