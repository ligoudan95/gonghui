# 02 存档、重试与数据一致性策划案

> 文档版本：R1.0
> 状态：冻结规则基线
> 适用：正式版存档、读档、重试和故障恢复；DEMO 使用 `DEMO/01-DEMO流程状态与存档结算案.md`
> 关联：[`00-修订总览与文档索引.md`](./00-修订总览与文档索引.md)、[`01-核心状态机与结算提交策划案.md`](./01-核心状态机与结算提交策划案.md)

## 1. 设计目标

存档系统要保护玩家时间，而不是保护玩家“只拿好处不承担代价”。本文件采用单机、无联网反作弊的前提，允许玩家利用重试学习战斗和路线，但不允许因读档或重复点击制造额外资源、奖励、支援次数或世界推进。

### 1.1 核心原则

- **R02-01 [冻结]** 存档是完整状态快照，不是只保存 UI 页面或部分变量。
- **R02-02 [冻结]** 正常加载只执行整包替换，不执行“当前存档 + 历史奖励”的字段合并。
- **R02-03 [冻结]** 结算提交由 `result_id` 和 `commit_id` 幂等保护。
- **R02-04 [冻结]** 战棋重试恢复战斗开始快照；它不把战斗前已提交的筹备结果回滚。
- **R02-05 [禁止]** 不用时间戳、随机文件名或 UI 是否关闭作为奖励是否领取的唯一依据。
- **R02-06 [冻结]** 手动存档不在战棋行动中开放；可及性设置、图鉴和日志阅读不改变游戏状态。
- **R02-07 [冻结]** 调试重置属于开发工具命名空间，不能由正式玩家存档加载或触发。

## 2. 存档层级

### 2.1 自动存档槽

正式版至少保留以下逻辑快照：

| 槽位 | 写入时机 | 用途 | 可否覆盖 |
|---|---|---|---|
| `AUTO_PREP` | 新周期进入 `PREPARING` | 回到周期开始 | 每个周期覆盖 |
| `AUTO_LOCK` | 出发锁定完成 | 恢复已锁定远征 | 当前远征唯一 |
| `AUTO_COMBAT_START` | 进入战棋 | 合法战棋重试基础 | 当前战棋唯一 |
| `AUTO_RESULT_PENDING` | 生成结果但未提交 | 防止结果丢失 | 当前结果唯一 |
| `AUTO_SETTLED` | 结果提交事务完成 | 结算后继续 | 每次提交生成新 epoch |
| `AUTO_CYCLE_CLOSED` | 周期维护和世界推进完成 | 进入下一周期 | 每个周期覆盖 |

### 2.2 手动存档

- 正式版至少一个手动槽；建议后续再提供多个槽位，但不能改变一致性规则。
- 手动保存时写入完整 `WorldState`、版本号、`settlement_epoch`、`last_commit_id` 和摘要。
- `COMBAT` 阶段拒绝手动保存；`RESULT_PENDING` 是否允许由正式版体验测试决定，初测建议只允许保存未提交结果的只读恢复点。
- 手动存档名称显示周期、任务、阶段和最近结果，避免玩家误读。
- 覆盖手动档前先写入临时文件并校验完整性，成功后原子替换；失败则保留旧档。

### 2.3 历史结算档

为了方便调试和玩家回顾，可保留只读历史摘要，但历史档：

- 不能直接作为普通游戏状态继续并入另一个档。
- 不能从历史档复制物品、资金、经验或助力次数。
- 只能整体加载为一个旧的 `settlement_epoch`，后续所有发展从该快照开始。
- 若正式版决定允许分支回溯，必须显式显示“将放弃当前 epoch 之后的所有进度”。

## 3. 存档数据契约

```text
SaveEnvelope
  save_id
  save_schema_version
  created_at
  slot_type
  game_build_id
  settlement_epoch
  cycle_id
  global_phase
  current_expedition_id
  current_result_id
  last_commit_id
  checksum
  payload
  recovery_status
```

`payload` 至少包含：

- 资源账本的 committed、reserved、debt 分栏。
- 当前任务实例、节点状态、世界事件、势力和政策。
- 冒险者状态、支援状态、NPC 支线阶段。
- 随机种子及每条随机流的游标。
- 一次性奖励的 `claim_key` 集合。
- 已消费回响的 ID 集合。
- 设置和可及性选项中会影响体验的部分，但不改变已锁定难度和奖励。

### 3.1 `settlement_epoch` 语义

- 每次成功结算事务后增加 1。
- 同一 epoch 内的手动存档可以互相整包替换。
- 读取旧 epoch 后，当前状态即回到该 epoch；不把新 epoch 的奖励、日志或 NPC 进度合并进来。
- 任何已经提交的 `commit_id` 在其所在 epoch 内只能执行一次。

## 4. 自动存档与事务边界

### 4.1 必须自动保存的位置

1. 新周期创建后。
2. 出发锁定成功后。
3. 战棋初始化完成后。
4. 结果对象创建后。
5. 结算事务完整提交后。
6. 周期关闭和维护完成后。

自动存档不能在“只写了一半字段”的中间阶段宣称成功。推荐使用：

```text
write temp -> flush -> checksum -> rename -> update slot index
```

### 4.2 崩溃恢复

加载时按以下顺序选择：

1. 校验最新完整槽位。
2. 若最新槽损坏，选择同一槽位最近的有效备份。
3. 若存在未完成 `commit_id`，根据事务日志判断是“未提交”还是“已提交待写档”。
4. 已提交的事务只恢复最终状态，不重复执行增量。
5. 未提交的事务回滚到该事务开始前快照。
6. 向玩家显示“恢复到上次完整结算”，不伪装成正常成功。

### 4.3 半结算防护

以下组合均属非法持久化状态：

- 任务已完成但 `result_id` 为空。
- 奖励已增加但 `claim_key` 未写入。
- 支援次数已扣但 `assist_usage_id` 为空。
- 世界事件已推进但 `settlement_epoch` 未增加。
- 结算摘要显示已提交，但 `last_commit_id` 不存在。

检测到非法状态时，开发版本应阻断并输出诊断；玩家版本应加载最近完整快照并记录错误报告。

## 5. 战棋重试与读档的区别

| 行为 | 允许时机 | 恢复范围 | 是否创建新世界周期 |
|---|---|---|---:|
| 战棋重试 | `RESULT_PENDING` 且可重试 | 战棋开始快照 | 否 |
| 接受失败/撤退 | `RESULT_PENDING` | 提交当前结果，进入结算 | 否，结算后 +1 epoch |
| 读 `AUTO_COMBAT_START` | 远征中断或合法重试 | 整个战棋开始状态 | 否 |
| 读 `AUTO_SETTLED` | 结算后 | 已结算完整状态 | 否 |
| 读旧手动档 | 任意可加载阶段 | 整包替换为旧 epoch | 以后从该旧状态继续 |

“读取战棋前档”不是“读取任意远征前档”：已提交的任务、地图助力和采购不能被战棋前档重新获得。

### 5.1 重试快照字段

```text
CombatRetrySnapshot
  expedition_id
  quest_instance_id
  settlement_epoch_before_combat
  map_state_before_combat
  party_state_before_combat
  resource_ledger_before_combat
  assist_state_before_combat
  combat_state
  expedition_seed
  random_stream_cursors
  objective_flags_before_combat
  combat_attempt_id
```

重试只恢复这些字段对应的战斗开始版本。所有战斗内的临时变化均丢弃，不能把临时战利品写进永久账本。

## 6. 唯一领取与重复提交

所有一次性奖励使用稳定键：

```text
claim_key = reward_id + quest_instance_id + node_id + event_version
```

以下行为必须幂等：

- 重新打开结算界面。
- 点击领取按钮两次。
- 结算完成后重新读取 `AUTO_RESULT_PENDING`。
- 从旧手动档重新执行同一节点。
- 节点版本更新后重访旧节点。
- 同一支线阶段重复触发回响。

相同 `claim_key` 已存在时：

- 不再次增加奖励。
- 不再次扣除资源。
- 可以显示“该奖励已领取”而不是报错。
- 生成低优先级审计日志，便于发现 UI 重复请求。

## 7. 失败、撤退与接受结果

失败和撤退必须是正常可继续的状态，不是隐藏的读档提示。

### 7.1 接受结果

玩家确认接受结果后：

1. 锁定当前 `result_id`。
2. 按 `01` 的顺序提交资源、队伍、任务、地图、世界和 NPC 变化。
3. 清理只属于当前战斗的重试快照。
4. 生成结算日志和下一步钩子。
5. 写入 `AUTO_SETTLED`。

### 7.2 失败后补救

补救内容可以在回城后提供，但不能重新打开已结束的战棋来抹除结果。补救必须是新任务实例或新服务调用，拥有独立：

- `recovery_quest_id`。
- 成本、期限和失败后果。
- 结果和奖励键。
- 与原任务的因果链接。

### 7.3 读档与失败结果

玩家可以通过读取失败前的旧档重新做选择，这是单机游戏的正常能力；但系统不能在同一存档中同时保留失败后的债务和成功后的奖励。加载旧档代表放弃该档之后的所有进度，界面必须明确提示。

## 8. 存档版本与迁移

### 8.1 版本字段

- `save_schema_version`：字段和结构版本。
- `game_build_id`：内容和脚本版本。
- `content_revision`：任务、节点和 NPC 配置版本。
- `settlement_epoch`：游戏内结算序号。

### 8.2 迁移规则

- 只允许单向迁移到当前版本。
- 迁移前备份原档，迁移后重新计算校验和。
- 新增字段使用明确默认值，不从相邻字段猜测。
- 无法安全迁移的存档标记为只读历史档，并提示玩家，不悄悄丢失内容。
- 内容版本更新新增奖励时，使用新的 `event_version` 和 `reward_id`；不能重新激活旧领取标记。

### 8.3 调试存档隔离

开发工具可以提供：

- 跳转阶段。
- 设置资源。
- 重置结果。
- 重放事件。
- 清空测试 claim。

这些操作必须写入 `debug_namespace = true` 的存档，正式版加载器拒绝读取该字段，避免测试工具制造玩家可用的复制路径。

## 9. 数据一致性故障矩阵

| 故障 | 恢复目标 | 玩家看到的提示 |
|---|---|---|
| 写档前崩溃 | 最近完整槽 | “已恢复到最近一次完整结算。” |
| 结算日志已写、快照未写 | 重放或加载提交后的完整状态 | “正在恢复已完成的结算。” |
| 快照校验失败 | 最近备份 | “当前存档损坏，已载入备份。” |
| 重试过程中强退 | 战棋开始快照 | “战棋未提交，已回到战斗开始。” |
| 结果预览中强退 | 同一 `result_id` 结果预览 | “上次结果尚未提交。” |
| 回响中强退 | 未消费回响队列 | “回响尚未全部处理。” |
| 周期关闭中强退 | 关闭事务前或后完整状态，不允许半推进 | “已恢复周期结算。” |

## 11. 实施任务

1. 定义 `SaveEnvelope`、`settlement_epoch` 和事务日志结构。
2. 为奖励、支援、节点、回响和结果建立稳定 claim/commit ID。
3. 实现自动槽位、手动槽位、临时写入和校验恢复。
4. 实现战棋开始快照和重试恢复。
5. 实现整包加载，禁止跨 epoch 字段合并。
6. 为结算、周期关闭和回响队列增加幂等接口。
7. 设计版本迁移和坏档恢复测试夹具。
8. 完成 TC02-01 至 TC02-12 后，再接入大量内容分支。
