## 1. 目标与不可破坏约束

本文件只解决一件事：定义一次行动从准备到结束时，系统处于什么状态、什么操作合法，以及结算怎样只提交一次。

### 1.1 冻结规则

- **R01-01 [冻结]** 世界时间只在行动周期关闭事务中推进；菜单、阅读日志、移动节点和战棋回合不直接推进世界周期。
- **R01-02 [冻结]** 所有会改变资源、任务、地图、队伍、NPC 或世界状态的操作必须归属于一个事务，并产生唯一 `commit_id`。
- **R01-03 [冻结]** 同一个 `result_id` 只能成功提交一次；重复请求必须返回“已提交”而不是再次执行。
- **R01-04 [禁止]** 任何内容分支不得绕过状态机直接修改最终资源或跳过结算日志。
- **R01-05 [冻结]** 战棋重试回到战棋开始快照，不能回到任意中间回合；它不产生第二份奖励，也不保留第一次尝试的战斗内收益。
- **R01-06 [冻结]** 结算提交后，普通读档不得把已经提交的结果合并到旧状态；只能整包加载一个合法快照。
- **R01-07 [冻结]** 主角是领队与决策者，不自动占用冒险者出战棋子名额；具体人数由 `07` 和 DEMO 文件定义。

### 1.2 名词

| 名称 | 定义 |
|---|---|
| 行动周期 `cycle_id` | 一次筹备、远征、结算和回响组成的最小世界推进单位 |
| 远征 `expedition_id` | 一个周期中从出发锁定到远征结果提交的行动实例 |
| 节点访问 `node_visit_id` | 一次进入节点的访问记录，不等同于奖励领取记录 |
| 结果 `result_id` | 一次任务/战棋结果的稳定唯一 ID |
| 结算提交 `commit_id` | 对一组结果、资源和世界变化执行一次原子提交的 ID |
| `settlement_epoch` | 已提交的世界快照序号；成功结算后单调递增 |
| 战斗快照 | 进入战棋前记录的完整战棋状态，可用于合法重试 |
| 周期快照 | 周期边界的完整游戏状态，可用于自动/手动存档 |
| local tick | 远征内部的移动、营地和战棋回合计数，不推进世界周期 |

## 2. 全局状态模型

实现至少需要保持以下逻辑分区。具体数据类型可以由程序决定，但字段语义不能改变。

```text
WorldState
  cycle_id
  settlement_epoch
  global_phase
  current_quest_id / quest_instance_id
  current_expedition_id
  world_event_states
  faction_states
  policy_state
  resource_ledger
  adventurer_states
  special_npc_states
  map_states
  assist_states
  save_schema_version
  last_commit_id
  event_log_cursor
```

### 2.1 顶层阶段

```text
PREPARING
PREP_LOCKED
EXPEDITION
RESULT_PENDING
SETTLED
ECHO
CYCLE_CLOSED
```

`EXPEDITION` 内部再使用：

```text
NODE
COMBAT
CAMP
WITHDRAWAL_PENDING
```

内部子阶段变化不增加 `cycle_id`，但应增加 `local_tick` 或对应的事件序号，防止重复提交。

### 2.2 阶段可执行矩阵

| 阶段 | 允许操作 | 禁止操作 | 自动保存 |
|---|---|---|---|
| `PREPARING` | 查看、有限筹备动作、组队、选择任务、推进非出发支线 | 直接改写世界已提交结果、领取同一奖励两次 | 周期开始、重要选择后可选 |
| `PREP_LOCKED` | 确认队伍、补给、政策、难度、联络位 | 改主目标、替换出发配置、反悔已扣除的不可退费用 | 锁定完成后必须保存 |
| `EXPEDITION/NODE` | 移动、调查、营地、节点选择、合法撤退 | 回工会重配队伍、修改已锁定支援、领取未满足条件的结果 | 进入关键节点前 |
| `EXPEDITION/COMBAT` | 战棋行动、目标选择、撤退、合法支援 | 手动存档、切难度、改变出发配置、跳过结果提交 | 战棋开始快照、战棋结束待结算快照 |
| `RESULT_PENDING` | 查看结果预览、选择接受结果或合法重试 | 领取部分结果后再重试、重复点击提交、改写前置条件 | 进入该阶段必须保存 |
| `SETTLED` | 查看结算、进入回响 | 再次领取奖励、撤销已提交资源和世界后果 | 提交完成后必须保存 |
| `ECHO` | 处理短回响、选择下一支线/下一钩子 | 修改已提交的任务结果、重复触发同一回响奖励 | 回响完成后可保存 |
| `CYCLE_CLOSED` | 读取摘要、进入下周期 | 在周期外再次维护、重复推进世界 | 关闭事务必须保存 |

## 3. 合法状态转换

### 3.1 主流程

```text
PREPARING
  -> PREP_LOCKED       由玩家确认出发配置触发
  -> EXPEDITION        出发成本预留成功后触发
  -> RESULT_PENDING    任务/战棋产生可提交结果后触发
  -> SETTLED            接受结果并完成原子提交
  -> ECHO               结算摘要写入后触发
  -> CYCLE_CLOSED       回响处理和周期维护完成
  -> PREPARING          创建 cycle_id + 1
```

### 3.2 节点和战棋分支

```text
EXPEDITION/NODE
  -> EXPEDITION/NODE    普通调查或移动
  -> EXPEDITION/CAMP    进入营地
  -> EXPEDITION/COMBAT  进入战棋
  -> WITHDRAWAL_PENDING 选择撤退
  -> RESULT_PENDING     节点直接产生任务结果

EXPEDITION/COMBAT
  -> EXPEDITION/COMBAT  普通战棋回合
  -> RESULT_PENDING     战棋目标满足成功、部分成功或失败条件
  -> WITHDRAWAL_PENDING 满足撤退条件或玩家发起撤退
```

### 3.3 非法转换处理

任何非法转换都必须：

1. 不改写 `WorldState`。
2. 生成 `state_transition_rejected` 日志，包含当前阶段、目标阶段、操作来源和拒绝原因。
3. 向玩家显示可理解原因，例如“战棋进行中不能更换队伍”。
4. 不消耗随机数、资源、支援次数或时间。

## 4. 出发锁定事务

玩家在 `PREPARING` 确认出发时，执行 `lock_expedition()`：

1. 校验任务仍可接受、期限未过期、队伍可出战、基础资源足够。
2. 生成 `expedition_id` 和 `expedition_seed`。
3. 创建出发配置快照：任务实例、队伍、补给、情报、政策、难度、联络位、已选择支援。
4. 将可退还的预留资源标记为 `reserved`，而非立即视为最终消耗。
5. 锁定本周期不能改变的字段。
6. 写入 `PREP_LOCKED` 自动存档。
7. 事务成功后进入 `EXPEDITION`。

出发锁定失败时：

- 所有预留资源释放。
- `expedition_id` 不进入可结算状态。
- 玩家回到 `PREPARING`，不能留下半个任务实例。

### 4.1 锁定字段

| 字段 | 出发后是否可改 | 说明 |
|---|---:|---|
| 主任务实例 | 否 | 任务目标和政策承诺已绑定 |
| 出战成员 | 否 | 伤病等特殊强制事件只允许转化为可解释后果 |
| 难度 | 否 | 下周期才能调整；可及性设置例外 |
| 政策 | 否 | 本次任务使用接受时/锁定时版本，规则由 `04` 定义 |
| 已选支援 NPC | 否 | 不能看到结果后更换支援组合 |
| 远征随机种子 | 否 | 读取存档和重试沿用同一种子状态 |
| 未使用的可携带物资 | 部分 | 只允许消耗，不允许从工会追加 |
| 战术行动 | 是 | 战棋内正常决策 |

## 5. 结果待结算与结果等级

任务或战棋条件满足后，不直接发奖，而是创建不可重复的结果对象：

```text
ResultRecord
  result_id
  expedition_id
  quest_instance_id
  result_type
  objective_flags
  optional_flags
  cause_factors[]
  pending_resource_delta
  pending_party_delta
  pending_world_delta
  pending_npc_delta
  pending_log_entries[]
  retry_allowed
  created_at_local_tick
  committed_at_epoch = null
```

结果类型：

- `FULL_SUCCESS`：主要目标和关键可选目标完成。
- `COST_SUCCESS`：主要目标完成，但至少一种可见代价生效。
- `PARTIAL_SUCCESS`：保住部分目标，未完成目标转化为后续内容。
- `WITHDRAWAL`：保全队伍和已获得信息，未完成目标进入世界后果。
- `FAILURE_CONTINUES`：核心目标失去，但产生补救、追责、营救或阵营变化。

### 5.1 结果公平性要求

结果预览必须展示：

- 已完成和未完成的目标。
- 将要获得和将要损失的资源。
- 伤病、疲劳、压力和士气变化。
- 敌方、势力、地图和特殊 NPC 后果。
- 是否可以重试、重试回滚什么。
- 接受结果后是否会关闭支线或触发期限。

“接受结果”不能被设计成隐藏惩罚；玩家可以不知道全部剧情，但必须知道后果类别和不可逆边界。

## 6. 统一结算顺序

`commit_result(result_id)` 必须在一个原子事务内按以下顺序执行：

1. **幂等检查：**若 `result_id` 已有 `committed_at_epoch`，直接返回已提交结果，不执行任何增量。
2. **校验快照：**确认结果属于当前 `expedition_id`，且没有被重试或取消。
3. **提交资源账本：**结算收入、消耗、预留释放、债务和一次性奖励。
4. **提交队伍状态：**写入伤病、疲劳、压力、士气、氛围和短期标签。
5. **提交任务状态：**标记任务完成、部分完成、撤退、失败或转化。
6. **提交地图状态：**写入节点调查、路线、警戒、证据和奖励领取标记。
7. **提交世界与势力状态：**更新期限后果、敌方行动、势力态度和城镇变化。
8. **提交特殊 NPC：**更新支线阶段、支援次数、冷却和使用反馈。
9. **写入因果日志：**每个增量绑定 `source_id`、旧值、新值和解释文本。
10. **写入 `commit_id` 和 `settlement_epoch`：**结果进入不可重复提交状态。
11. **生成结算摘要：**按任务、队伍、支援、工会和世界分类显示。
12. **自动保存：**只在事务完整成功后写入 `SETTLED` 快照。

任一校验失败时，整笔事务回滚，不得留下“已扣费但未完成任务”或“已完成任务但未发奖励”的半状态。若磁盘写入在提交后失败，下一次加载通过 `commit_id` 日志重放或恢复最近完整快照，但不得重新执行增量。

## 7. 战棋重试规则

战棋重试是容错功能，不是额外奖励渠道。

### 7.1 合法重试

- 仅在 `RESULT_PENDING` 且 `retry_allowed = true` 时出现。
- 恢复进入战棋前的完整战斗快照：资源、支援次数、临时状态、目标进度、随机流游标、敌我位置和战棋事件状态。
- 战棋开始前已经提交的地图助力、购买情报或筹备成本不恢复。
- 重试不改变 `expedition_seed`，但允许玩家采用不同战术获得不同合法结果。
- 重试后生成新的 `combat_attempt_id`，但沿用同一 `result_id` 组；旧尝试结果标记为 `discarded_attempt`，不进入世界账本。
- 战棋内获得的经验、物品、证据和日志只有被接受的最终结果才会提交。

### 7.2 禁止行为

- 不能在重试后保留第一次尝试的经验、掉落或支援使用次数变化。
- 不能通过重试改变已锁定的难度、政策、出战成员和任务实例。
- 不能先接受结果领取奖励，再读取战棋前存档继续领取另一份奖励。
- 不能用重试绕过已提交的周期维护、支线后果或任务期限。

## 8. 中断、崩溃和强退

| 中断位置 | 恢复策略 |
|---|---|
| `PREPARING` | 恢复最近完整周期快照；未提交的界面选择丢弃 |
| `PREP_LOCKED` | 恢复锁定快照；若已成功预留，进入远征准备界面，不重复扣费 |
| `EXPEDITION/NODE` | 恢复最近安全节点快照或节点开始快照；未提交的临时选择丢弃 |
| `COMBAT` | 恢复战棋开始快照或最近合法回合点；不得创建第二个结果 |
| `RESULT_PENDING` | 重新显示同一 `result_id`；不得自动选择成功或失败 |
| `SETTLED` | 加载已提交的 `settlement_epoch`；不重复结算 |
| `ECHO` | 恢复回响队列和已消费的回响 ID；不重复发放回响奖励 |
| `CYCLE_CLOSED` | 加载新周期快照；不重新进行维护和世界推进 |

实现可选择更细的恢复点，但不能比上述边界更宽松地恢复或重复执行。

## 9. 因果日志契约

所有可见数值变化都必须记录：

```text
LogEntry
  log_id
  cycle_id
  settlement_epoch
  commit_id
  source_type       # quest/node/combat/assist/maintenance/recovery
  source_id
  target_type       # resource/party/map/npc/faction/world
  target_id
  old_value
  new_value
  reason_key
  player_text
  reversible = false/true
```

示例：

```text
source_type: assist
source_id: SUP-GUIDE-RETREAT
 target_type: map
 target_id: NODE-MINE-06
 old_value: locked
 new_value: available
 reason_key: assist_route_opened
 player_text: “向导用一次人情打开了西侧撤退点；本次远征结束后该点关闭。”
```

日志不是调试专属内容；玩家结算页至少看到 `player_text` 和变化分类，制作团队可看到完整字段。

## 10. 规则验收用例

| ID | 场景 | 预期 |
|---|---|---|
| TC01-01 | 直接重复提交同一 `result_id` | 第二次返回已提交，不重复资源、奖励、阶段或日志 |
| TC01-02 | 结算中强退 | 重载后继续同一结果，不出现半结算 |
| TC01-03 | 战棋失败后重试 | 战斗开始快照完全恢复，战前地图助力不恢复 |
| TC01-04 | 重试后取得不同结果 | 只有最终接受结果进入账本，旧尝试无奖励 |
| TC01-05 | 结算后读取旧手动档 | 整包切换，不与已提交结果合并，不复制奖励 |
| TC01-06 | 战棋中尝试手动存档 | 操作被拒绝，不消耗资源和随机流 |
| TC01-07 | 非法从战棋回到工会 | 被拒绝并记录原因 |
| TC01-08 | 节点结果和任务结果同时提交 | 使用同一 `commit_id`，只推进一次周期 |
| TC01-09 | 结果预览后取消 | 不提交任何结果，不扣未提交资源 |
| TC01-10 | 结果接受后关闭游戏 | 加载后进入已结算界面，不能再次领取 |

以上用例在 `09` 和 `DEMO/06` 中必须有实际执行记录；未执行不得标记为通过。

## 11. 实施任务与依赖

1. 建立稳定 ID 和 `settlement_epoch` 字段。
2. 编写阶段转换表和非法操作拦截。
3. 实现资源账本事务接口，禁止内容脚本直接修改最终值。
4. 实现结果对象、`result_id` 幂等提交和回放日志。
5. 实现战棋开始快照、重试恢复和最终接受结果。
6. 实现自动存档点与故障恢复检查。
7. 对接 `03`–`08` 的增量字段和日志原因。
8. 完成 TC01-01 至 TC01-10 后，才能进入 DEMO 内容量扩充。
