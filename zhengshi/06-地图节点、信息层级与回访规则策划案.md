# 《未定名：冒险者工会》06-地图节点、信息层级与回访规则策划案

> 文档版本：R1.0；状态：正式版规则基线，数值仍需原型实测。
> 适用范围：区域节点、信息层级、事件进度、可通行性、奖励状态、回访、撤退与快通。
> 依赖：00 索引以及 01–05 的状态、结算、资源、支援契约；本案不定义 DEMO 的具体 8 节点、单位或数值。
> DEMO 映射文件：[DEMO/04-DEMO地图节点与主战棋结果案.md](DEMO/04-DEMO地图节点与主战棋结果案.md)。支援映射见 [DEMO/03-DEMO特殊NPC支援与无支援基础解法案.md](DEMO/03-DEMO特殊NPC支援与无支援基础解法案.md)。

## 1. 设计目标与硬边界

R06-01：地图必须支持“未知但可推理”，而不是靠反复踩点或随机硬卡主线。
R06-02：信息层级、节点事件进度、可通行性、奖励状态是正交字段；不把所有状态塞进一个枚举。
R06-03：主线关键线索必须有多来源固定可得路径，特殊 NPC、推荐职业和单次随机事件不能成为唯一门票。
R06-04：回访保留历史、已获得事实和奖励领取记录；新事件只能叠加开放，不能重置旧奖励。
R06-05：物理证据是否带回由携带容量、证据实体和撤离结果判定；情报事实由 `fact_id` 集合独立记录。
R06-06：快通只节省 UI 操作和表现时间，不省略明确的 `world_cycle`、`local_tick`、补给、伤病、暴露和支援成本。
R06-07：事件版本变化只开放新的 `reward_id`；不重发旧奖励、不重置旧 claim。
R06-08：数值和 DEMO 内容均是待实测/待主代理配置，不在此案声称已实现或测试通过。

## 2. 统一周期与节点所在阶段

全局流程固定为 `PREPARING -> PREP_LOCKED -> EXPEDITION(NODE/COMBAT) -> RESULT_PENDING -> SETTLED -> ECHO -> CYCLE_CLOSED`。
R06-09：节点移动、调查、营地、快通和回访行为均只能发生在 `EXPEDITION/NODE`，不得偷偷推进 world cycle。
R06-10：一个 world cycle 只在 `CYCLE_CLOSED` 事务成功后递增一次；地图内行为只增加 `local_tick`。
`world_cycle` 表示跨周期世界节拍；`local_tick` 表示本次远征内的移动、停留、休整和节点动作成本。
主线事件的期限若依赖周期，写成明确的周期边界；若依赖远征内部风险，写成 local_tick 或暴露计数。

|动作|阶段|world_cycle|local_tick|允许的结果|
|---|---|---:|---:|---|
|进入节点|EXPEDITION/NODE|不变|按配置增加|读取状态、触发事件入口|
|节点调查|EXPEDITION/NODE|不变|按动作增加|新增事实、改变进度或产生代价|
|地图移动|EXPEDITION/NODE|不变|按边/路线增加|抵达另一节点、触发风险|
|营地休整|EXPEDITION/NODE|不变|按休整规则增加|恢复/伤病变化、触发局部事件|
|进入战棋|EXPEDITION/COMBAT|不变|按进入规则增加|建立战斗开始快照|
|撤退回城|RESULT_PENDING|不变|结算已发生的成本|物理证据按撤离判定|
|正式结算|SETTLED|不变|结束本次远征|账本和奖励幂等提交|
|周期关闭|CYCLE_CLOSED|+1 一次|重置/保留按规则|维护、冷却、世界推进|

## 3. 节点数据模型：四组正交字段

每个 `node_id` 至少保存四组互不替代的状态：`information_state`、`event_progress`、`traversal_state`、`reward_state`。
信息字段回答“玩家知道什么”；事件字段回答“事件做到哪一步”；通行字段回答“现在能否进入/离开”；奖励字段回答“哪些奖励已领取”。
禁止用 `cleared`、`visited` 或单个 `node_state` 代替四组数据；“已访问”不等于“已解决”，也不等于“已领奖”。

|字段组|建议字段|回答的问题|可否独立改变|
|---|---|---|---|
|信息层级|rumor/identified/mastered、facts_seen|玩家知道的风险、路线和事实|可以，调查或外部来源更新|
|事件进度|event_version、task_instance、stage、flags|本事件进行到哪一步|可以，选择和结果更新|
|可通行性|entry_open、exit_open、route_flags、block_reason|当前能否进入、通过、撤退|可以，世界或事件改变|
|奖励状态|claim_key、reward_id、claim_state、claimed_epoch|奖励是否已主张/领取|可以，结算事务更新|

`information_state` 建议从 `rumor -> identified -> mastered` 递进，但允许不同来源直接提供某一层；信息层级不反向自动宣告事件已完成。
`event_progress` 可为 `unstarted / active / resolved / failed_forward / abandoned` 等内容状态，但不是通行或奖励状态。
`traversal_state` 可同时有“入口开放、内部封锁、撤退开放”等多个布尔/集合字段；不要强迫节点只处于一个可通行枚举。
`reward_state` 只记录该奖励的主张状态；普通访问、事实发现和新版本事件不应自动重复领奖。

## 4. 信息层级与事实集合

信息层级是玩家认知的可读投影，权威事实以稳定 `fact_id` 保存；情报不是货币，不因查看地图或使用支援被扣除。
R06-11：主线必要事实必须由至少两种来源提供，来源可为公开委托、普通节点调查、队伍职业动作、工会设施或特殊 NPC 支援。
单一来源可以更快、更安全或附带额外解释，但不能是唯一的主线门票，除非该内容明确标为可选秘密。
信息 UI 同时显示来源可信度、获得时间、是否已验证和关联节点；“传闻”不能直接被当作已确认结果。

|信息级别|玩家可见内容|允许推断|不能承诺|
|---|---|---|---|
|rumor|地点主题、模糊危险、可能收益|值得调查的方向|精确敌人、完整路线和奖励|
|identified|主要风险、可选入口、关键目标类别|路线取舍和准备方向|所有事件后果必然确定|
|mastered|已验证机制、稳定路线、已解决变化|可规划快通和回访|新版本内容永远不变|

事实示例：`fact_missing_worker_last_seen`、`fact_seal_requires_two_marks`、`fact_north_exit_collapsed`。
如果一个节点被撤退，已经写入的 `fact_id` 仍保留；但“我看见证据”不等于“我把实体证据带回工会”。
删除或替换事实只允许通过规则明确的世界修订事务，不能因回访、失败或读档 UI 操作隐式删除。

## 5. 事件进度与任务实例

每次任务实例使用稳定的 `task_instance_id`；同一地图节点可承载多个任务实例，但事件进度必须按任务实例隔离。
`event_version` 表示内容规则版本，不是每次访问递增的次数；普通进入不会制造新版本。
事件进度至少保存进入前、进行中、已解决、失败前进、撤退保留和关闭原因，使结算能解释“为什么不能再选”。
一个事件的 `flags` 只写它拥有的事实和目标结果；不把奖励是否领取、节点是否通行混进 flags。
主线任务在失败后可以转为补救实例或追责实例；原实例不被伪装成成功，也不重置其旧选择。

|事件动作|event_progress|信息变化|通行变化|奖励变化|
|---|---|---|---|---|
|调查未完成|active|可能新增 fact|通常不变或局部暴露|不领取|
|解决主要问题|resolved|可升 mastered|开放/关闭按规则|解锁对应 reward_id|
|撤退|abandoned/failed_forward|保留已知 fact|敌情或期限可能变化|按携带和结果判定|
|战棋部分成功|failed_forward|新增结果事实|开放补救或封锁路线|只发已满足的奖励|
|事件版本更新|新 task/event version|可新增说明|可开放新入口|仅新 reward_id|

## 6. 可通行性、边与方向

地图边不能只保存“连接存在”；每条边至少有稳定 `edge_id`、入口条件、风险成本、出口条件和阻塞原因。
R06-12：可通行性是运行时计算的结果，基础配置、任务 flags、事实集合、当前队伍状态和支援效果共同参与。
“未发现”与“已封锁”必须区分：前者是信息不足，后者是已知存在但当前确实不能通过。
同一节点可以有安全长路、风险捷径和仅撤退方向；开放其中一条不自动开放所有边。
路线被关闭时，UI 显示关闭原因和至少一个可调查方向；不能让玩家靠撞墙猜规则。

|通行字段|示例值|作用|
|---|---|---|
|entry_open|true/false|是否可以从当前地图状态进入|
|exit_open|true/false|是否存在合法离开/撤退出口|
|route_flags|集合|如 `route_safe_known`、`route_hidden_open`|
|risk_profile|稳定配置|移动、补给、伤病或暴露的代价来源|
|block_reason|原因码|向玩家解释未开放/被封锁原因|
|requires_fact|事实集合|满足知识而非货币条件|

通行条件中的职业动作应优先提供替代办法，而不是硬锁；特殊 NPC 可以开启捷径，但基础边仍须覆盖主线需要。
若所有出口因结果关闭，必须提供回城、救援或接受失败的结果出口，不能形成地图软锁。

## 7. 奖励、claim_key 与反刷

R06-13：稳定领奖主键为 `claim_key = run_id + task_instance + node_id + reward_id + event_version`。
`run_id` 标识一次完整存档运行；`task_instance` 隔离同一主线的不同实例；`node_id` 固定归属地点。
`reward_id` 必须细分物品、资金、事实包、支援解锁、旗标和可重复服务；不能用一个“节点奖励”包揽所有效果。
`event_version` 只在内容规则需要新增可领取内容时改变；旧 reward 的 claim_key 不因新版本重算。
`node_visit_id` 仅追踪一次进入/访问，用于日志、耗时、暴露和调试，不得用作领奖 ID，也不得让每次访问生成新奖励。

|字段|用途|稳定性要求|
|---|---|---|
|run_id|区分存档运行|迁移时保持不变|
|task_instance|区分任务实例|重试不新建领奖实例|
|node_id|归属地点|内容重命名需迁移映射|
|reward_id|具体奖励单元|旧奖励永不因版本重复发放|
|event_version|事件规则版本|只开放新 reward|
|node_visit_id|访问追踪|可多次生成，不参与 claim 唯一性|

领取流程为 `unclaimed -> reserved -> claimed`；预览和事件展示不能直接写 `claimed`。
结算事务提交 claim 时验证当前任务结果、物理携带、资源容量和重复状态；重复请求返回已领取结果，不重复加减。
同一次事件有多个奖励时逐项写 claim；某个奖励不满足条件不得阻止其他已满足奖励正确结算。

## 8. 节点奖励与物理证据

奖励分为 `fact_reward`、`physical_reward`、`service_reward`、`resource_reward`、`world_flag_reward` 五类。
`fact_reward` 进入 facts 集合，可在撤退后保留；`physical_reward` 必须实际占用 carry，并受撤离和丢失结果影响。
`service_reward` 可能解锁支援、路线或设施行为；它不是可重复领取的货币，必须按 reward_id 记录。
`resource_reward` 按结算账本原子增加；`world_flag_reward` 改变事件/世界字段，但不能越权改写未满足的主线条件。

撤退时按三层判断物理证据：是否拾取、是否在 carry 快照中、是否通过合法出口撤离。
只获得事实而未携带实体证据时，日志明确写“已知真相保留、物证未带回”；不能既删事实又发完整物品奖励。
若物证在战斗中遗失，新的结果实例可以增加“证据损坏”事实，但不得重发旧物证 claim。

## 9. 回访、重复进入与局部刷新

R06-14：回访默认不重置奖励；已经 `claimed` 的 reward_id 不因离开节点、失败、回城或新周期而回到 `unclaimed`。
回访可以触发三类变化：新版本事件、世界状态变化、玩家尚未完成的事件阶段；每类变化都须在字段上可区分。
已解决的普通事件不得原样重播；若需要复述，使用摘要或“已解决”入口，不重新扣移动成本后发旧奖励。
重复进入可以增加 `node_visit_id` 和 `local_tick`，也可以触发可重复服务，但服务必须明确次数/冷却/成本。
节点的永久变化、周期变化、远征变化和访问变化分别记录，不能用一次“回访次数”推断所有状态。

|回访情形|信息|事件进度|通行|奖励|
|---|---|---|---|---|
|已解决普通节点|保持/可补充说明|resolved|按世界状态|旧奖励保持 claimed|
|未完成调查节点|可能新增 fact|active|按当前条件|未满足不发|
|新事件版本|新增提示|新 version 实例|可开放新边|只开放新 reward_id|
|世界旗标变化|更新 identified/mastered|旧事件不重置|重新计算边|旧 claim 不重发|
|失败后补救回访|保留旧事实|新 task_instance|开放补救路线|新 reward_id 独立 claim|

“可重复服务”不是一次性奖励，例如在已掌握营地休息；它仍须写明每次成本、冷却、恢复上限和是否增加 local_tick。
若内容设计需要再次取得同类资源，应创建可重复 service 或新的 reward_id，而不是清空旧 claim。

## 10. 撤退、失败前进与信息保留

R06-15：撤退是合法结果，不等于删除本次探索；已消费的情报、补给、local_tick 和支援代价按事务保留。
撤退保留 `facts`、已确认信息、任务失败/撤退状态和已产生的世界 flags；未满足的奖励不提前发放。
物理证据依据携带和撤离结算；未成功带回的实体奖励可以丢失，但不能影响已获得的事实集合。
撤退后可开放补救任务、追踪路线或新的事件版本；补救不是把原事件伪装成成功。
战棋失败同理：目标 flags 和胜负不能在 `RESULT_PENDING` 之后被支援改写，除非该支援在规则中明确是结算前合法的结果转换。

|结果|保留|不保留/不自动给予|可新增|
|---|---|---|---|
|撤退|facts、消耗、失败前进状态|未撤出的物证、未达成奖励|补救/追责实例|
|部分成功|达成目标片段、带回物品|未达成目标与对应奖励|后续节点、风险事实|
|完全成功|已满足事实、物证和奖励|无|安全点、回访新事件|
|战棋失败|已写入事实和代价|胜利奖励、未撤出证据|伤病、敌方推进、补救|

## 11. 快通、路径压缩与明确成本

R06-16：快通只省略已经掌握的 UI 逐节点操作、重复演出和不需要重新决策的确认，不省略规则成本。
快通执行前必须展示摘要：经过的边、local_tick、补给/工具消耗、伤病/暴露风险、可能触发的事件和回城出口。
若路径包含可重复风险事件，快通使用预先明确的风险解析规则；不能暗中掷一次不可解释的隐藏结果。
快通遇到未掌握节点、未读新变化、重要抉择或资源不足时暂停并返回玩家，不自动替玩家作价值选择。
快通不能跳过支援调用的合法窗口、不能让 `world_cycle` 只因按钮按下而多次递增，也不能绕过结算幂等。

|快通步骤|需保留|可省略|
|---|---|---|
|路线确认|边条件和当前 flags|逐个节点动画|
|成本模拟|local_tick、补给、伤病、暴露|重复点击确认|
|已知事件|已掌握结果和规则|已看过文本|
|新事件|停下交给玩家|无|
|结果回城|撤退/物证/奖励判定|重复表现|

## 12. 事件版本与内容迁移

事件版本升级的目的，是补充新的可玩内容或修正尚未领取的规则，不是给旧玩家重复发一遍已领取奖励。
R06-17：迁移表必须列出旧 `event_version`、新版本、旧 reward_id、可新增 reward_id 和已领取处理。
旧版本 claim 保持可验证；若 reward_id 被废弃，写 `retired` 而不是回退成 `unclaimed`。
新版本只对满足新增条件的实例开放新的 reward_id；玩家未再次访问时不自动领取，除非内容明确是周期结算奖励。
事件 flags 的语义若改变，必须建立迁移函数和回归用例，不能直接在加载时覆盖旧值。

实例：旧版本的 `reward_evidence` 已领取；新版本新增 `reward_followup_map`，回访后可以领取新地图，但不能重发 evidence。
实例：旧版本节点已 `resolved`，新版本增加补救任务；旧事件仍 resolved，补救用新 task_instance 和新 claim_key。

## 13. 主线多来源与反硬卡矩阵

|主线需求|来源 A|来源 B|可选来源 C|单一来源禁止项|
|---|---|---|---|---|
|目标位置|公开委托摘要|普通调查节点|支援解析|禁止只靠恋爱/单 NPC|
|敌方机制|职业观察|情报室档案|特殊 NPC 远程分析|禁止随机一次成功才知|
|安全出口|地图探索|战棋目标提示|向导支援|禁止撤退无任何出口|
|物证用途|委托人说明|节点证词|事实拼接|禁止携带物证才知任务目的|
|补救方向|失败结算摘要|回城日志|新委托传闻|禁止失败后只显示 game over|

每个来源写明可见时间、可靠性和成本；多来源不是复制同一段文本，而是让玩家可以从不同系统获得同一关键事实。
若某来源暂时不可用，其他来源仍应在合法游玩路径内出现；玩家可以付出更长路线、更多风险或较低奖励作为交换。

## 14. 具体节点实例

实例 A：节点先处于 rumor；公开委托给出“旧矿道可能有失踪者”，调查节点得到目标位置 fact，职业观察揭示塌方风险。
实例 B：向导支援开放隐藏捷径，但只改变通行字段和 local_tick；它不自动把未解决事件改为 resolved，也不领取奖励。
实例 C：玩家在战棋失败后撤退，证词 fact 已保留，携带的物证未通过出口；回城开放补救任务，旧物证 claim 仍未领取。
实例 D：玩家回访已解决的营地；旧奖励保持 claimed，营地服务可以再次使用，但每次休整有明确补给/刻度成本。
实例 E：新版本新增后续调查 reward_id；旧证据奖励不重发，旧任务 instance 保持 resolved，新任务 instance 独立推进。
实例 F：快通经过两个 mastered 节点；系统省略演出，但按路线计算 local_tick、补给、暴露和伤病，并在新事件前暂停。

## 15. 验收用例（只定义，不代表已执行）

TC06-01：同一节点同时存在 rumor、active、entry_open 和 unclaimed reward，逐项修改并确认四组字段互不覆盖。
TC06-02：通过两种不同来源取得同一主线 fact；禁用任一来源仍能从另一合法来源继续。

## 17. 与其他文档的接口契约

与 01 的接口是阶段、结果提交、`result_id` 幂等和 `settlement_epoch`；本案不得自行创建第二套结算状态。
与 02 的接口是整包存档、重试快照、旧手动档只读和跨阶段 merge 禁止；节点 claim 不得绕开存档规则。
与 03 的接口是资金、补给、carry、声望和维护；情报 facts 不得当作可消费货币接入经济账本。
与 04 的接口是 `world_cycle`、`local_tick`、周期关闭和任务生命周期；移动与营地不能偷偷推进世界周期。
与 05 的接口是 NPC 支援状态、联络位、地图干预次数、高影响干预槽和无支援基础解法。
与 07–09 的接口是冒险者状态、随机公平、反漏洞测试和交付门禁；本案不重写职业、伤病或战棋公式。

## 18. 结论

地图系统的权威不是一个漂亮的“已完成”图标，而是四组可审计字段共同说明玩家知道什么、事件做到什么、哪里能走以及奖励是否已领取。
事实和物证分离让撤退有代价但不抹掉玩家知识；稳定 claim_key 与 node_visit_id 分离让回访有内容但不允许刷奖。
多来源线索、基础通路、可解释快通和新版本只开放新奖励，共同保证探索既有推理空间又不依赖隐藏硬卡。
任何后续地图、节点或战棋内容都必须能映射到本案字段、时序、成本、回访和验收规则。
