# 案 2《时间与日历系统规划案》

## 1. 系统定位与目标

- **定位**：全局唯一时间标尺——经营（休息/招募刷新）、委托（时限倒计时）、冒险（出征耗时）全部挂在此标尺上；提供「日结算」统一调度点，杜绝各系统各自计时导致的时序混乱。
- **服务的核心体验**：委托时限的紧迫感与经营节奏感（「今天该接哪单、派谁出门、家里谁在休息」的日程决策）。

## 2. 机制细则

### 2.1 日历制定义（已定稿）

- 以**「天」**为最小单位；委托以剩余天数倒计时，到时刷新、消失或替换（原文）。
- **推进方式（推断建议）**：**行为驱动、非实时流逝**——天数只在发生「耗时行为」时推进，玩家不行动时间不走（无真实时间压力，契合单机与移动端碎片化节奏）；**兜底主动行为「等待/跳过一天」（已定稿·用户拍板 2026-09-22·第三轮拍板组·方案 A）**：无任何耗时行为可用时（如全队重伤休养、无力招募）可主动跳过一天推进日历，防日历死锁软锁——见 2.2 表。
- 历法显示（推断）：以「第 N 天」计数为主，七日一周星期展示增强经营氛围（DEMO 必做，#19）；**开局日=周 1（周首）**——与委托板开局预生成对齐（案 6 §2.2·第四轮拍板组·方案 A）：开局当日不触发周刷新，首个周刷新=第 8 天日结算；不设季节/昼夜系统（完整版可选扩展，DEMO 外）。
- **「每日」边界定义**：见 §2.3。

### 2.2 时间消耗行为表（推断建议）

| 行为 | 时间消耗 | 规则说明 |
|---|---|---|
| 出征探索 | 总出征耗时 = 案 7 地图「基础出征耗时」+ Σ 事件耗时（案 8），DEMO 基础 1 天 | 出征为「离城」状态；**耗时申报时点=回城批量结算（已定稿·用户拍板 2026-09-22·第三轮拍板组）：出征执行期间日历冻结（天数不推进、无到期判定），回城时一次性申报总出征耗时→日历累加推进并逐日补结算后台事务与期间到期委托（见 2.3/2.5）**；#3+案 16 裁定：地图定义为权威，案 6「预估」仅展示 |
| 战棋战斗 | 不单独耗天 | 含在出征日内（避免频繁跳日破坏节奏；高强度战斗是否+1 天留数值专项验证） |
| 事件检定/分支 | 不单独耗天 | 部分事件选项可标注「耗时+1 天」类代价（推断：作为事件资源之一，归案 8） |
| 设施生产 | 生产设施不消耗天数，直接产出 | 2026-09-22 用户拍板（02 案手改确认），暂缓设施启用时同口径 |
| 重伤休养 / 普通损耗恢复 | 按天 / 自动 | 重伤休养：按天（战败自动触发，无需指派；#21：DEMO 内唯一按天恢复项）；普通损耗恢复：自动恢复制（回城自动进入恢复状态，无需指派；DEMO 当日全额、完整版按天随日结算，#18） |
| 招募池刷新 | 每日 | 日结算时刷新 |
| 委托倒计时 | 每日 -1 | 日结算时结算，归零触发到期处理 |
| 公会内管理操作（接委托/编队/浏览/交易） | 0 天 | 管理行为不耗天，保持节奏流畅 |
| **等待/跳过一天（主动兜底）** | 1 天 | 无任何耗时行为可用时的主动推进：点击「等待」按钮 → 日历 +1 并执行完整日结算（重伤休养倒计/普通损耗恢复/招募池刷新/委托倒计时照常）——**防全队不可出征软锁**（战败全队休养+无力招募时日历不死锁）；按钮入口 UI 归案 15【已定稿·用户拍板 2026-09-22·第三轮拍板组·方案 A】 |

### 2.3 并行规则（随 #9 解绑重写，#23/#24 后修订）

- **出征日 = 公会后台日**：任一队伍出征消耗的天数内，公会中的休息、休养照常逐日推进——**结算时点=回城批量补结算（出征期间日历冻结，回城申报耗时后逐日补跑日结算，玩家一次看到后台累计结果；第三轮拍板组 2026-09-22）**（生产为直接产出、无逐日推进——2026-09-22 口径）；
- **并行时间口径（#23/#24 后修订）**：战斗委托同时最多 1 个进行中（案 6），多队伍同时离城场景不复存在；非战斗委托（存档）不出征、按日自动推进（挂日结算）；连续多次出征的耗时仍逐次累加推进日历（每次出征独立申报，案 6 §2.4 时间结算）；
- **「每日」边界定义（照改）**：本系统所有「每日」表述（每日一次出征、每日刷新、每日恢复）一律以日结算为界——日结算执行即视为进入新的一天，逐日计数与「当日」标记在日结算时刷新；
- **「每名冒险者每日一次出征」为防御性约束（照改注明）**：当前基础出征 1 天模型下自然满足，防零耗时往返场景；
- 一天内「出征 + 回城管理 + 再次编队」允许（只要相关冒险者当日未再出征）。

### 2.4 日结算流程（固定顺序，推断建议）

```
1. 天数 +1，日历刷新
2. 设施生产无日结算事务（2026-09-22 用户拍板：生产不耗时、下单直接产出——原「进行中生产推进/完成交付」废除；暂缓设施启用时同口径）
3. 恢复结算：重伤休养倒计推进 + 普通损耗自动恢复（仅普通损耗 DEMO 即时结算；重伤休养 DEMO 仍按天挂本步骤）（案 5，#18）
4. 压力/怪癖每日结算（暂缓系统，DEMO 跳过，案 14）
5. 招募池刷新（案 5）
6. （暂缓）商店库存刷新（案 4，完整版启用）
7. 委托倒计时 -1 → 到期委托处理（见 2.5）；**每周第 1 天的日结算直接执行周刷新（清空重生成），当日跳过常规到期处理**（跳过仅限**板上**委托到期表现处理；已接挂单委托的倒计时与到期失败照常执行）（到期表现不单独触发，已定稿 D5；案 6）——委托时限建议 ≤7 天与周对齐（数值案定）；**时限 N 天=上板日+N 天到期（不含上板当日）；新上板委托当日结算不递减**【已定稿·用户拍板 2026-09-22·二审拍板组】
8. 非战斗委托进度推进与完成结算（工期制，无到期失败，案 6，D4）（#24·完整版存档，DEMO 跳过——按日自动推进工期）
9. 日期触发的剧情/节日事件检查（暂缓系统，DEMO 跳过，案 13；第 9 步=**章节开幕检查**：章节闸门满足后的日结算触发主线开幕演出/委托授予【完整版存档，DEMO 跳过】；终战软时限倒计时挂本步【完整版】，案 19）
10. 汇总通知（新一天提示：恢复完成/委托到期/新候选，单弹窗汇总避免打扰）
```

### 2.5 委托到期处理（原文+推断细化）

- **板上未接委托**到期：从委托板移除，是否补位及补几个由委托模板到期行为配置决定（刷新/消失/替换三种表现，允许板空，归案 6，#10）；
- **已接取未完成委托**到期：自动判定失败（推断建议）——**挂单未出征到期：自动失败、从挂单列表移除**；**出征执行期间日历冻结、无到期判定（回城批量结算口径，第三轮拍板组 2026-09-22）——回城申报耗时推进日历时，期间跨过到期日的挂单委托按到期失败结算；出征委托自身于回城时先行结算（成功/战败/撤退），原「出征进行中到期：队伍自动回城」分支在该口径下不可达、由上述结算顺序覆盖**；完整版是否扣声望及数额**留数值专项案**（DEMO 内建议无惩罚，降低学习成本）。

### 2.6 时间上限

无全局天数上限、无整体倒计时（推断：单机自由节奏；完整版主线是否设节点时限归案 13 另议）。

## 3. 数据与配置需求（字段级草案）

| 配置 | 字段建议 |
|---|---|
| 总控时间配置 | 起始天数、星期显示开关（七日循环）、结算顺序 pipeline（阶段 ID 列表，支持插拔暂缓项） |
| 行为耗时表 | 行为 ID、基础天数（仅通用行为；出征耗时唯一归属案 7 地图定义，案 16 裁定） |
| 委托时限（归案 6，本案引用） | 委托模板.时限天数（命名归案 6）、到期行为（刷新/消失/替换） |
| 招募刷新（归案 5，本案引用） | 刷新周期（天）、池容量 |

非战斗委托工期字段归案 6 委托模板，本案仅提供日结算调度挂点（维持「耗时唯一归属」原则）。

## 4. 与其他系统的接口

- **输入**：各系统申报的耗时行为（出征耗时←案 7/6；恢复结算（自动恢复制，案 5）——生产不耗时直接产出、无耗时申报，2026-09-22 口径）；
- **输出**：日结算广播（按 2.4 顺序逐项通知）：恢复完成→案 5；池刷新→案 5；委托到期→案 6；日期事件→案 13；
- **依赖**：无上游（全局基础）；
- **被依赖**：案 3（休息效率结算时机）、案 6（倒计时）、案 5（恢复/刷新/休养天数）、案 7（出征耗时）、案 4/14（每日结算挂点）。

## 5. DEMO 口径

- **做**：天数推进（行为驱动）、星期显示（必做，#19）、日结算流程的 1/3/5/7/10 步（跳过暂缓步）、委托倒计时与到期处理（板上三种表现；已接到期失败且无惩罚）、出征耗时（基础出征耗时 1 天，占位，权威归案 7 地图定义；申报时点=回城批量结算，§2.2）、事件选项「耗时」代价（DEMO 做 1 处演示，#3）、重伤休养按天（唯一按天恢复项）、普通损耗回城当日全额、**等待/跳过一天按钮（软锁兜底，第三轮拍板组·方案 A，§2.2）**；
- **不做（暂缓存档）**：生产耗时结算（2026-09-22 拍板废除：生产不耗时直接产出，完整版亦不设）、压力怪癖每日结算、日期剧情/节日事件、多档区域耗时修正（如需，归案 7 地图定义扩展，本案不设）；
- DEMO 验证点：日结算汇总通知是否清晰、出征跳日的节奏感受。

## 6. 风险与待专项细化项

- **风险**：① 出征日并行推进的后台结算对玩家不透明（界面必须清晰展示「离家期间公会发生了什么」，UI 归案 15）；② 多队连出征造成天数快速堆积，委托时限压力失衡（数值匹配验证；#9/#23 后人力与按人头出征频次为实际闸门——每名冒险者每日最多一次出征、战斗委托同时 1 个进行中）；③ 日结算顺序变更会引发连锁时序问题（顺序表进配置而非硬编码）；
- **待数值专项案**：各行为具体耗时、区域耗时修正（如需，归案 7 地图定义扩展，本案不设）、委托时限与耗时的匹配曲线、已接委托到期失败的声望惩罚值、休养天数。
